상식 퀴즈 시스템 설계

초보자용 설명서 · 물리적 구조(어떤 장비가 어디에 있나)와 논리적 구조(프로그램이 어떤 층으로 나뉘나)를 함께 본다.

0. 먼저 알아둘 말

용어쉬운 설명
브라우저(클라이언트)사용자가 쓰는 크롬·사파리. 게임 화면이 여기서 돌아간다.
서버항상 켜져 있으면서 요청을 받아 답을 주는 프로그램. 여기서는 NAS 안에서 돈다.
DB(데이터베이스)데이터를 정리해 담아 두는 저장소. 여기서는 파일 하나(quiz.db)로 된 SQLite를 쓴다.
API브라우저가 서버에 "이거 줘/이거 저장해" 하고 말하는 약속된 주소들. 예: /api/ranking
Docker 컨테이너프로그램과 실행 환경을 한 상자에 담은 것. NAS에서는 Container Manager 앱이 상자를 돌려 준다.
리버스 프록시바깥 요청을 받아 안쪽 프로그램에 전달해 주는 문지기. HTTPS(자물쇠) 처리도 맡는다.
포트포워딩공유기가 "바깥에서 443번으로 온 요청은 NAS로 보내라"고 길을 열어 주는 설정.

1. 물리적 구조 — 장비가 어디에 있나

사용자 기기는 인터넷을 거쳐 집 공유기에 닿고, 공유기가 요청을 NAS로 넘긴다. 서버 프로그램과 DB 파일은 모두 NAS 한 대 안에 있다.

번호별 역할

  1. 리버스 프록시: 바깥에서 오는 요청을 받아 퀴즈 서버로 넘기고 HTTPS 자물쇠를 붙인다.
  2. Container Manager: 퀴즈 서버를 상자(컨테이너)에 담아 실행한다. NAS가 재부팅돼도 자동 재시작되게 설정한다.
  3. quiz.db: 문제와 순위 기록이 들어 있는 파일. 컨테이너를 지워도 남도록 NAS 폴더에 연결(볼륨 마운트)해 둔다.
  4. Hyper Backup: quiz.db를 정기 백업한다. 이 파일이 곧 모든 기록이다.

보안 메모: NAS 관리 화면(DSM, 5000/5001번)은 바깥에 열지 않는다. 열어 둘 길은 퀴즈용 443번 하나뿐이다. DSM 계정에는 2단계 인증을 켠다.

2. 논리적 구조 — 프로그램이 어떤 층으로 나뉘나

왼쪽은 브라우저에서 도는 부분, 오른쪽은 NAS 안 서버에서 도는 부분이다. 가운데 선이 둘을 잇는 API다. 브라우저의 화면과 게임 로직은 저장 방식을 모르고, storage.js라는 창구만 부른다. 그래서 저장 방식을 기기 저장에서 서버로 바꿔도 화면 코드는 그대로다.

층을 나누는 이유

  • 화면/로직/저장 분리: 문제가 생겼을 때 어느 층을 볼지 정해진다. 디자인을 바꿔도 점수 계산이 안 깨진다.
  • storage.js 한 곳: 1~3단계에서는 기기 저장으로 만들고, 4단계에서 이 파일 안쪽만 서버 호출로 바꾼다.
  • 서버에서 점수 재계산: 브라우저가 보낸 점수를 믿지 않고, 보낸 답안으로 서버가 다시 계산해 점수 조작을 막는다.

데이터 표(DB 테이블)

표열설명
questionsid, category, text, choice1~4, answer_index, explanation문제 40개. 서버 시작 시 비어 있으면 questions.js 내용으로 채운다.
recordsid, nickname, total_score, history_score, science_score, geography_score, general_score, played_at한 판이 끝날 때마다 한 줄 추가. 순위는 total_score 내림차순, 같으면 played_at이 빠른 순.

3. 한 판의 흐름 — 요청이 오가는 순서

서버와의 통신은 판 시작 때 1번, 끝날 때 1번뿐이다. 40문제를 푸는 동안은 통신이 없어서 NAS가 느려도 게임이 끊기지 않는다.

5. 단계별 구조 — 1~4단계에서 무엇이 어떻게 자라나

같은 층 구조(화면 → 게임 로직 → storage.js → 저장소)를 단계마다 한 층씩 채워 간다. 아래 그림에서 초록은 그 단계에 새로 만드는 것, 주황은 그 단계에 고치는 것, 흰색은 이전 단계 것을 그대로 쓰는 것이다.

1단계 — 뼈대, 문제 데이터, 저장 창구

  • 만드는 것: public/ 폴더 뼈대, 문제 40개(questions.js), storage.js(기기 저장판), 문제 검증 스크립트
  • 구조상 의미: 가장 아래층(저장 창구)부터 만든다. 화면이 아직 없어도, 나중에 서버로 갈아끼울 접점이 처음부터 정해진다.
  • 장비: 내 PC. 서버 없음.
  • 끝났다는 기준: 검증 스크립트 통과(카테고리별 10개, 보기 4개, 정답 번호 범위, id 중복 없음).

2단계 — 핵심 게임 흐름

  • 만드는 것: app.js(화면 전환), game.js(출제·채점·점수), 시작·문제·피드백 화면
  • 구조상 의미: 위 두 층이 생긴다. 화면은 로직만 부르고, 로직은 storage.loadQuestions()로만 문제를 받는다. 답안은 원본 보기 순서 기준 번호로 기록해 4단계 서버 채점과 맞춘다.
  • 장비: 내 PC. 서버 없음.
  • 끝났다는 기준: 40문제를 끝까지 풀고 총점·카테고리별 점수가 맞다. 한 판이 3~4분 안에 끝난다.

3단계 — 결과, 순위, 마감

  • 만드는 것: 카테고리 전환 화면, 결과 화면, 순위표, 다시 하기, 이어하기
  • 구조상 의미: saveRecord()와 loadRanking()이 처음 실제로 쓰인다. 서버가 없어도 완성된 게임이며, 이 상태가 4단계의 "롤백 지점"이 된다.
  • 장비: 내 PC. 순위는 이 기기 안에만 있다.
  • 끝났다는 기준: 키보드만으로 완주, 360px 폭에서 레이아웃 유지, 순위 정렬·동점 테스트 통과.

4단계 — 서버 추가와 NAS 배포

  • 만드는 것: server/(라우터·서비스·저장소·시드), SQLite DB, Dockerfile, docker-compose.yml, NAS 배포 README
  • 구조상 의미: storage.js 안쪽만 서버 호출로 바꾼다. 화면과 게임 로직은 수정하지 않는다. 서버가 점수를 다시 계산하고, 서버가 죽으면 기기 저장으로 대체된다.
  • 장비: 1장의 물리 구조도 전체. 집 안만 쓰면 NAS와 같은 Wi-Fi 기기만, 집 밖에서도 쓰려면 공유기·도메인·HTTPS까지 필요하다.
  • 끝났다는 기준: 서로 다른 두 기기에서 같은 순위표가 보인다. 서버를 끄면 기기 저장으로 동작한다. 서버 테스트 통과. NAS 실기기 배포는 직접 확인한다.

3단계까지 끝나면 서버 없이도 완성된 게임이다. 4단계는 같은 게임을 NAS로 옮기는 작업이다.
