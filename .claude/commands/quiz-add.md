`public/js/questions.js`(문제은행)에 새 퀴즈를 추가해줘. 문제 수는 아래 `$2`로 정한다(없으면 1문제). 기존 문제와 같은 형식으로 만들고, 아래 검증을 모두 통과한 문제만 파일에 추가한다.

## 입력

- 카테고리: `$0`
- 난이도: `$1`
- 문제 수: `$2` (비었으면 1. 1~100의 정수만 허용한다. 100을 넘거나 정수가 아니면 만들지 말고 "문제 수는 1~100 사이 정수여야 합니다."라고만 알려 준다.)

### 카테고리 (`$0`)

| 입력 | category | id 접두사 |
|---|---|---|
| history, 한국사 | history | h |
| science, 과학 | science | s |
| geography, 지리 | geography | g |
| general, 일반상식 | general | n |

### 난이도 (`$1`)

| 입력 | 의미 |
|---|---|
| 쉬움, easy | 초등~중학교 수준 상식. 오답 보기가 정답과 확연히 다르다. 대부분 바로 맞힌다. |
| 보통, medium | 성인이 알 법하지만 헷갈릴 수 있다. 오답 보기가 그럴듯하다. |
| 어려움, hard | 정확한 연도, 수치, 구분을 알아야 한다. 매력적인 오답이 있다. 단, 논란이 있거나 자료마다 값이 다른 사실은 쓰지 않는다. |

- 난이도는 **새 문제를 얼마나 어렵게 낼지** 정하는 데만 쓴다. 지금 문제 데이터 형식에는 난이도 필드가 없고 점수에도 쓰지 않으므로, 파일에 난이도를 기록하지 않는다.
- 카테고리나 난이도가 비었거나 표에 없으면 문제를 만들지 말고 "사용법: /quiz-add <카테고리> <난이도> [문제 수] (카테고리: history, science, geography, general / 한국사, 과학, 지리, 일반상식, 난이도: 쉬움, 보통, 어려움)"이라고만 알려 준다.

## 여러 문제를 만들 때 (문제 수가 2 이상)

시간이 오래 걸려도 되니 **속도보다 정확성**을 우선한다. 아래 순서를 지킨다.

- **한 문제씩** 만든다. 아래 1~4단계(파악, 작성, 검증, 추가)를 문제 하나에 대해 끝까지 마친 뒤 다음 문제로 넘어간다. 여러 문제를 한꺼번에 만들어 두었다가 같이 추가하지 않는다. 그래야 중간에 끊겨도 그때까지 추가된 문제는 검증을 마친 상태로 남는다.
- **주제를 겹치지 않게** 고른다. 같은 카테고리 안에서 이미 낸 주제(이번 실행에서 만든 것 포함)와 같은 사실을 묻지 않는다. 시작 전에 해당 카테고리의 기존 문제를 모두 읽고, 이번에 낼 주제를 하위 영역(예: 지리라면 한국 산·강, 세계 수도, 대륙과 대양, 나라와 지역 등)별로 고르게 나눠 계획한다.
- **목표 수를 채우지 못해도 된다.** 근거를 확인하지 못해 배제한 주제는 건너뛰고 다른 주제로 바꾼다. 확인되는 주제를 더 찾지 못하면 억지로 채우지 말고 거기서 멈춘다.
- **추가할 때마다** 4단계의 `npm run validate`로 통과를 확인한다. 10문제마다 `node --test server/service.test.js server/game.test.js`도 실행한다. 실패하면 그 문제를 되돌리고 원인을 알린 뒤 멈춘다.
- **진행 상황**을 10문제마다 한 줄로 알려 준다(예: "지리 20/100 추가, 배제 3").
- 정답 위치는 매 문제 `npm run validate`가 출력하는 분포를 보고, 가장 적은 번호 쪽으로 둔다.

## 1. 기존 문제 파악

- `public/js/questions.js`에서 해당 카테고리의 문제들을 읽고, 쓰인 형식과 어조, 기존 주제를 파악한다.
- 새 id는 접두사 + 두 자리 번호로, 그 카테고리에서 가장 큰 번호보다 1 큰 값으로 한다(예: `h10`이 마지막이면 `h11`). 번호는 중간이 비어 있어도 재사용하지 않는다.
- 기존 문제와 **같은 사실이나 같은 정답**을 묻는 문제는 만들지 않는다. 질문 문구가 달라도 같은 내용이면 중복이다.

## 2. 문제 만들기

한 문제는 `questions.js`에서 다음 한 줄 형식으로 쓴다. 키를 따옴표로 감싼 JSON 형태를 유지한다.

```
  { "id": "h11", "category": "history", "text": "…?", "choices": ["…", "…", "…", "…"], "answerIndex": 1, "explanation": "…", "source": "기관 '항목' (수치나 연도) URL" },
```

- `choices`는 정확히 4개이고, 서로 달라야 하며, 비어 있으면 안 된다. 원본 순서이며 `answerIndex`(0~3)는 그 순서 기준 정답 번호다.
- `text`는 한 문장 질문이다. 정답이 하나로 정해져야 한다.
- `explanation`은 한 문장이고 **40자 이하**다. 기존 해설처럼 "…이다/했다." 형태로 쓴다.
- `source`는 필수이고 기관·항목명과 URL을 포함한다. 기존 문제의 `source` 형식을 따른다.
- 정답 위치가 몰리지 않게, 현재 정답 위치 분포(`npm run validate`가 출력하는 0~3번 분포)에서 가장 적은 번호 쪽으로 둔다.

## 3. 검증 (모두 통과해야 추가한다)

이 프로젝트의 원칙은 **모든 문제의 출처가 명확해야 하고, 의심스러운 내용은 배제**하는 것이다.

1. **사실 확인**: WebSearch로 정답과 해설의 근거를 찾고, 근거가 될 페이지를 WebFetch로 열어 **본문에 그 사실이 실제로 나오는지** 확인한다. 기억이나 추측으로 쓰지 않는다. 가능하면 백과사전, 정부·국제기관, 공식 사이트 등 1차 또는 신뢰할 수 있는 자료를 쓴다.
2. **출처 URL**: `source`의 URL은 실제로 열어서 확인한 주소만 쓴다. 지어내거나 확인하지 않은 URL을 쓰지 않는다. 열리지 않거나 근거가 없으면 다른 출처를 찾는다.
3. **의심스러운 내용 배제**: 자료마다 다르게 말하거나, 출처를 하나도 확인하지 못하거나, 논란이 있는 사실이면 그 주제로는 문제를 만들지 않는다. 다른 주제로 바꿔 처음부터 다시 만든다. 그래도 확인되는 문제를 못 만들면 파일을 수정하지 말고 이유를 알려 준다.
4. **모호한 표현**: 질문, 보기, 해설에 `가장|최초|최대|최고|최소|최저|최장|최단|최신|최다|최상|최하|제일|유일|으뜸`이 있으면 비교 범위, 측정 기준, 측정 주체와 시점, 포함 대상이 문제 안에 분명한지 본다(`/quiz-validate`와 같은 기준). 분명하지 않으면 문구를 고쳐서 명시하거나 그 표현을 쓰지 않는다.
5. **형식과 중복**: 위 2번 형식을 지켰는지, id가 겹치지 않는지, 기존 문제와 같은 사실이 아닌지 확인한다.
6. **난이도**: 입력한 난이도에 실제로 맞는지 스스로 점검한다. 어색하면 보기나 질문을 조정한다.

## 4. 파일에 추가

- 검증을 통과했을 때만 `Edit`로 `questions.js`에 한 줄을 추가한다. 같은 카테고리 문제들 가장 마지막 줄 바로 아래, 다음 카테고리 앞의 빈 줄 위에 넣는다. 그 밖의 줄은 건드리지 않는다.
- 추가한 뒤 `npm run validate`를 실행해 **통과하는지 확인**한다. 실패하면 원인을 고쳐 다시 실행하고, 고칠 수 없으면 추가한 줄을 되돌린다.
- 이어서 `node --test server/service.test.js server/game.test.js`를 실행한다. 실패하면 알려 준다. `npm test` 전체는 DB 모듈(better-sqlite3)이 설치돼 있어야 해서 이 PC에서는 실행되지 않을 수 있다. 실행되지 않았으면 그 사실을 그대로 적는다.

## 5. 결과 보고

문제 수가 2 이상이면 문제마다 길게 쓰지 말고, 추가한 문제를 `id | 질문 | 정답 | source 기관·항목` 표로 정리한다. 배제한 주제와 이유(근거 불명, 자료마다 다름 등)는 따로 목록으로 적는다. 목표 수보다 적게 추가했으면 몇 개 부족한지와 이유를 알려 준다. 다음을 간단히 알려 준다.

- 추가한 문제: id, 카테고리, 난이도, 질문, 보기 4개와 정답, 해설 (문제가 여러 개면 위 표로 대신한다)
- 출처: `source` 내용과, 열어서 확인한 근거 한 줄(어떤 문구로 사실이 확인됐는지)
- 검증 결과: 위 6개 항목과 `npm run validate`, 테스트 실행 결과를 각각 통과/실패/미실행으로
- 카테고리별 문제 수 변화

마지막에 아래를 꼭 알려 준다.

- 이 변경은 **커밋하거나 push하지 않았다**.
- NAS의 DB는 문제가 **비어 있을 때만** `questions.js`에서 채워지므로, 새 문제는 NAS를 업데이트해도 DB에 들어가지 않는다. 게임에 반영하려면 README 5번 항목의 "문제를 고친 뒤 반영" 방법(DB 초기화 등)이 필요하다.
